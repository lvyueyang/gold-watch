# 实时行情监控与规则告警系统设计方案

## 1. 背景与目标

- 为黄金与股票等标的提供多源实时/准实时价格监控。
- 支持以“规则”为单位配置触发条件与通知方式，如：
  - 当价格到达 1140 元时发送通知；
  - 当价格到达 1160 元时再次发送通知；
  - 通知方式支持：飞书/企微/钉钉 Webhook，支持自定义 Webhook 地址。
- 提供可视化管理后台：维护标的、规则、Webhook、查看触发记录与投递日志。
- 目标特性：稳定、低延迟、可扩展、易运维、具备幂等与去抖动能力。

## 2. 核心功能

- 标的管理：添加/编辑/删除黄金、股票等监控对象（Instrument）。
- 数据采集：对接多个行情源（轮询/推送），统一聚合为标准价格流。
- 规则管理：以标的为维度配置多个触发规则，支持多种条件与生效窗口。
- 告警投递：根据规则触发通过平台适配器（飞书/企微/钉钉）发送消息。
- 去抖动与抑制：防止“价格来回触发”与高频重复通知。
- 审计与可观测：保存触发记录、投递结果、失败重试与系统指标。

## 3. 概念与术语

- Instrument：监控标的（如 XAU、某 A 股、ETF）。
- Price Tick：标准化的价格事件（时间戳、买一/卖一/中间价、来源）。
- Rule：规则，定义触发条件（如到达/突破/回落/区间/涨跌幅）与通知动作。
- Alert：一次规则触发的“告警事件”。
- Delivery：一次告警在某通知渠道上的“投递尝试”。
- WebhookConfig：通知渠道配置（平台类型+URL+签名/密钥+模板参数）。

## 4. 典型用例

1. 为“沪金主力合约”添加两条规则：到达 1140、1160 即通知。
2. 当价格在 1140±1 范围上下波动时，系统只触发一次“到达 1140”的通知，并在回避时间（如 10 分钟）内抑制重复。
3. 多平台并发投递，任何平台失败均会重试，并保留日志与错误码。

## 5. 系统架构

### 5.1 组件划分

- 数据源适配层（Data Sources）
  - 多个行情源适配器（HTTP 轮询、WebSocket、第三方 SDK）。
  - 标准化输出为统一的 Price Tick。
- 价格总线（Price Bus）
  - 接收所有来源的 Tick，合并去重，按标的路由。
- 规则引擎（Rule Engine）
  - 基于最新状态与历史窗口评估规则；管理“已触发状态”与抑制窗口。
- 告警调度器（Alert Orchestrator）
  - 为每个触发的 Alert 生成投递任务，写入投递队列并追踪状态。
- 通知适配层（Notifier Adapters）
  - 飞书/企微/钉钉适配器，统一接口，模板化渲染与签名计算。
- 存储与状态（Storage）
  - 配置库（标的、规则、Webhook）、运行态（最后价格、规则状态）、审计库（Alert/Delivery 日志）。
- 管理控制台（Admin UI）
  - CRUD 配置、规则测试、一键试发、日志与指标面板。

### 5.2 数据流（文本示意）

```
行情源1/2/3 → 数据源适配 → Price Bus → 规则引擎
                                      ↓
                                 Alert 生成
                                      ↓
                            告警调度器 → 投递队列 → 平台适配器（飞书/企微/钉钉）
                                      ↓
                                 审计存储/指标
```

## 6. 数据源与采集策略

- 接入方式
  - HTTP 轮询：固定周期拉取最新价，适合免费或限流 API。
  - WebSocket/流：实时推送，适合交易所或第三方实时源。
  - 混合：主用 WS，兜底轮询。
- 标准化
  - Tick: `{ instrumentId, price, ts, source, bid?, ask?, mid? }`
  - 统一时区（UTC），统一精度（decimal/string + 精度字段）。
- 可靠性
  - 多源合并：优先级/时间戳择优；源异常自动降级。
  - 防抖：同毫秒内重复 Tick 合并；大幅波动优先处理。

## 7. 规则引擎设计

### 7.1 规则模型

```
Rule {
  id: string
  instrumentId: string
  name: string
  type: 'touch' | 'cross_up' | 'cross_down' | 'range' | 'pct_change'
  params: {
    target?: number            // 目标价（到达/突破）
    lower?: number, upper?: number  // 区间
    pct?: number               // 百分比（如 2%）
    windowMs?: number          // 计算窗口（涨跌幅/区间）
    holdMs?: number            // 触发需保持时间（如连续 3 秒）
  }
  notify: {
    channels: WebhookRef[]     // 可多选
    throttleMs?: number        // 两次触发最小间隔
    dedupWindowMs?: number     // 去重窗口
    suppressUntilReset?: boolean // 达成一次后需手动/条件复位
  }
  active: boolean
  schedule?: { tz: string, days?: number[], start?: string, end?: string } // 交易时段
  createdAt, updatedAt
}
```

类型说明：

- touch（到达）：价格首次进入 [target - ε, target + ε] 触发；默认 ε=0（可配置）。
- cross_up（上穿）：从小于 target 到大于等于 target 的边界穿越触发。
- cross_down（下穿）：反向穿越触发。
- range（区间）：进入/离开某区间触发，可拆分为两条子规则。
- pct_change（涨跌幅）：在 windowMs 内相对上一参考价涨跌超过阈值触发。

### 7.2 状态机与去抖动

- 为每条规则维护 State：
  - lastValue：上次价格；
  - lastFiredAt：上次告警时间；
  - inWindow：是否处于触发条件内；
  - cooldownUntil：抑制期结束时间；
  - refPrice：参考价（用于 pct_change）。
- 触发判定：
  - 满足条件且不在 cooldown；
  - 若 holdMs>0，需在持有窗口内连续满足后触发；
  - suppressUntilReset 时，只在从“不满足→满足”边沿触发一次，直到离开条件后复位。

### 7.3 示例（满足用户描述）

- 规则 A：触发条件为 touch(target=1140)，channels=[飞书/企微/钉钉 中任意配置]。
- 规则 B：触发条件为 touch(target=1160)，channels 同上。
- 两条规则相互独立，均有各自的去抖动与冷却设置。

## 8. 通知与 Webhook 适配

### 8.1 统一接口

```
Notifier.send({
  channel: 'lark' | 'wecom' | 'dingtalk',
  webhookUrl: string,
  secret?: string,     // 某些平台需要签名
  title: string,
  text: string,
  card?: object,       // 平台卡片内容（可选）
  dedupeKey?: string,  // 幂等去重键
})
```

### 8.2 消息模板（示例）

- 标准文本：
  - 标的：{instrumentName}
  - 价格：{price}
  - 规则：{ruleName}（{type}/{target}）
  - 时间：{ts}
  - 链接：{detailUrl}

### 8.3 平台差异

- 飞书（Lark）：支持文本、卡片消息；部分需要签名；机器人 Webhook。
- 企微（WeCom）：文本/Markdown/卡片；支持关键字/签名。
- 钉钉（DingTalk）：文本/Markdown/ActionCard；需 timestamp+sign。

统一通过适配器处理签名与 Content-Type，并在失败时返回平台错误码。

### 8.4 重试与幂等

- 幂等：对每次 Alert 生成 dedupeKey（ruleId+instrumentId+bucket），平台侧重复返回 200 亦认为成功。
- 重试：指数退避（如 5s/30s/2m/10m），上限 N 次；可配置死信队列。
- 日志：保存 request/response 摘要与状态码、重试次数。

## 9. 存储设计（关系型或 KV + 索引）

- instruments(id, symbol, name, exchange, precision, status, createdAt, updatedAt)
- quotes_last(instrumentId, price, ts, source)
- rules(id, instrumentId, name, type, params(json), notify(json), active, schedule(json), createdAt, updatedAt)
- rule_states(ruleId, instrumentId, lastValue, inWindow, lastFiredAt, cooldownUntil, refPrice, state(json))
- alerts(id, ruleId, instrumentId, price, ts, payload(json), status, createdAt)
- deliveries(id, alertId, channel, webhookUrlHash, status, attempt, lastError, createdAt, updatedAt)
- webhooks(id, name, channel, urlHash, secretHash, config(json), createdAt, updatedAt)
- users(id, email, role, prefs(json), createdAt, updatedAt)（如需权限）

说明：

- Webhook/Secret 均只保存 hash/加密密文，严禁明文。
- 读写路径拆分：配置写少读多，日志写多读少，必要时冷热分层。

## 10. API 设计（REST/JSON）

- GET /api/instruments
- POST /api/instruments
- GET /api/rules?instrumentId=
- POST /api/rules
- PATCH /api/rules/:id
- POST /api/webhooks（保存名称+平台+URL+密钥）
- POST /api/rules/:id/test（以当前价格试发）
- GET /api/alerts?instrumentId=&ruleId=
- GET /api/deliveries?alertId=

鉴权建议：管理端需登录态（JWT/Session），投递/采集内部服务通过服务密钥。

## 11. 管理控制台（前端）

- 信息架构与导航
  - 顶部/侧边导航：仪表盘、标的、实时行情、规则、Webhook、告警、投递、审计、设置、健康。
  - 全局搜索：按标的/规则名/ID 搜索并快速跳转到详情。
  - 全局状态：环境标识（staging/prod）、队列 backlog 指示灯、版本信息。

- 页面清单与功能细节 0) 登录页（Login）
  - 路由：/login（仅在启用“会话 Cookie 模式”时生效；默认 Basic Auth 仍可作为回退方式，见第 19 章）
  - 目标：统一入口登录管理台，改善 Basic 原生弹窗体验；校验成功后设置短期会话 Cookie 并跳转 /admin
  - 表单：
    - 用户名（必填）
    - 密码（必填）
    - 记住登录（可选，启用时将 Cookie Max-Age 设为 7 天；未勾选则为会话期）
  - 交互：
    - 支持 Enter 提交；提交中按钮禁用并显示加载；提交失败聚焦错误提示
    - 错误类型区分：401 凭证错误、429 尝试过多（显示剩余等待时间）、其他网络错误
    - 成功后跳转：优先使用 URL 中的 redirect 参数（同域校验），否则跳转 /admin
  - 安全：
    - 后端采用常数时间比较；不记录明文凭证与 Authorization 头
    - 返回 Set-Cookie: goldwatch_sid=<签名值>; HttpOnly; Secure; Path=/; SameSite=Lax; Max-Age=<可选>
    - CSRF：登录接口使用双提交 Cookie 或者基于 SameSite=Lax；受保护写操作的 API 再加自定义 X-CSRF-Token（后续实现）
    - 失败限速：基于 IP/指纹的尝试计数与退避（429），避免暴力猜测
  - API：
    - POST /api/auth/login
      - 请求：{ username, password, remember?: boolean } 或 Authorization: Basic
      - 成功：200 + Set-Cookie（金签名会话）；body { ok: true }
      - 失败：401（凭证错误），429（超过尝试上限），5xx（服务错误）
    - POST /api/auth/logout
      - 行为：清除 goldwatch_sid；返回 204
  - 可访问性：
    - label/aria-describedby、aria-invalid、aria-live=polite 输出错误
    - 屏幕阅读器顺序与视觉顺序一致；焦点环可见
  - 兼容与回退：
    - 若浏览器阻拦第三方 Cookie 或 Set-Cookie 失败，页面提示改用 Basic Auth（示例 curl -u）或在同浏览器会话中访问受保护资源触发原生弹窗
  - 文案：固定简体中文，不做国际化与多语言
  1. 仪表盘（Dashboard）
     - KPI 卡片：监控标的数、启用规则数、近 24h 告警数、投递成功率。
     - 趋势图：告警趋势、投递成功率曲线、采集延迟分布（分钟级）。
     - 最近事件：最新 10 条 Alert 与 Delivery（可点击跳转详情）。
     - 系统状态：定时采集最近运行时间、队列 backlog、失败率。
     - 快捷操作：新建规则、新建 Webhook、批量启停规则入口。
     - 空态与错误：当无数据或采集失败时给出指引与重试按钮。
  2) 标的管理（Instruments）
     - 列表：symbol、名称、交易所、精度、状态、最近价、更新时间、关联规则数、操作。
     - 筛选/排序：按状态、交易所、最近更新时间排序；关键字搜索。
     - 操作：新增/编辑/删除标的、启用/停用监控（不等同于规则启停）。
     - 详情页：基本信息、最近价格曲线（近 24h）、关联规则列表、最近 N 次 Tick。
     - 批量：CSV 导入/导出（可选）；批量停用/启用监控。
     - 校验：精度与交易时段设置必填；symbol 唯一。

  3) 实时行情（Quotes）
     - 视图：表格/卡片两种展示；支持固定列与列宽记忆。
     - 字段：最新价、涨跌幅%、来源、更新时间（相对时间 + 绝对时间）、采集延迟。
     - 刷新：顶部刷新开关（自动/手动），显示上次刷新时间；高频场景建议最小 5s。
     - 工具：选中标的一键“创建规则”，自动带入标的。
     - 空态：提示添加标的或开启采集。

  4) 规则管理（Rules）
     - 列表：名称、标的、类型、参数摘要（target/区间/百分比）、启用状态、冷却（ms）、最近触发时间、操作。
     - 筛选：按启用状态、类型、标的、更新时间；支持批量勾选。
     - 操作：新建/编辑/复制/删除/启用/停用、批量启停、批量删除。
     - 新建/编辑表单：
       - 基本：规则名称、标的选择、规则类型（touch/cross_up/cross_down/range/pct_change）。
       - 参数：随类型动态渲染（target、lower/upper、pct、windowMs、holdMs）。
       - 通知：选择 Webhook 渠道（多选）、冷却（throttleMs）、去重窗口（dedupWindowMs）、suppressUntilReset。
       - 计划：交易时段（tz/days/start/end）。
       - 校验：数值范围、区间合法性、百分比与窗口依赖关系。
     - 详情页：
       - 基本信息与参数可视化（如阈值与最近价对比图）。
       - 通知渠道列表与最近投递概况。
       - 触发历史：触发时间线 + 价格快照；支持查询时间范围与导出。
       - 测试与模拟：
         - 试发：/api/rules/:id/test（以当前价或指定价模拟一次触发，不写入状态）；
         - 回放：上传/选择一段 Tick 数据进行本地评估（不产生真实投递）。
     - 启停：单条或批量切换 active；停用时可选清理冷却状态（见第 18 章）。

  5) Webhook 管理（Channels）
     - 列表：名称、平台（飞书/企微/钉钉）、URL Hash、签名/密钥状态、最近调用、成功率、操作。
     - 操作：新增/编辑/删除、禁用/启用、测试发送（携带示例 payload）。
     - 表单：平台选择、Webhook URL、签名/密钥（隐藏显示，支持重新写入）、消息模板预览。
     - 安全：只显示脱敏信息；修改密钥需二次确认；操作写入审计。

  6) 告警记录（Alerts）
     - 过滤：时间范围、标的、规则、状态（新建/已投递/失败/忽略）、严重级别（可选）。
     - 列：时间、规则、标的、触发价格、状态、投递数、失败数、操作。
     - 详情：告警 payload、触发时上下文（最近价窗口）、关联投递列表与状态。
     - 操作：再次发送、标记已处理/忽略、导出（CSV/JSON）、静音该规则一定时间（不改规则 active）。

  7) 投递日志（Deliveries）
     - 过滤：时间范围、渠道（飞书/企微/钉钉）、状态（成功/失败/重试中）、错误码。
     - 列：时间、渠道、Webhook、状态、耗时、尝试次数、错误摘要、操作。
     - 详情：请求/响应摘要（脱敏）、重试时间线。
     - 操作：手动重试（遵守退避与上限）、关联到 Alert/Rule。

  8) 审计日志（Audit）
     - 列：时间、操作人、目标（Rule/Webhook/Instrument/...）、动作（新增/编辑/启停/删除/重试）、结果、备注。
     - 检索：按时间/对象/动作过滤；支持导出。

  9) 设置（Settings）
     - 规则默认值：冷却、去重窗口、持有时间、默认抑制策略。
     - 交易时段：全局默认交易日与时间范围（规则可覆盖）。
     - 安全设置：IP 白名单（可选开关）、失败限速阈值。
     - 环境信息：Workers 版本、绑定 IDs（D1/KV/Queues）、最近部署时间。
     - 认证信息：仅展示“管理员认证已启用”，不显示 ADMIN_USER/ADMIN_PASS 值，提示通过 secrets 修改。

  10) 健康与状态（Health）
  - 定时任务：最近运行时间、耗时、是否成功；失败原因摘要。
  - 队列：backlog、失败率、消费者在线状态。
  - 外部依赖：Webhook 平台可用性探测（轻量 ping，结果仅提示）。
  - 自检：触发一次内部健康检查（不做真实投递）。

- 通用交互与规范
  - 列表：分页、排序、筛选、批量操作、导出；列选择与布局记忆。
  - 状态：空态占位、加载骨架、错误重试；长操作显示进度与可取消。
  - 可访问性：键盘导航、焦点环、ARIA 标注；移动端断点布局。
  - 表单：即时校验 + 提交校验；失败提示靠近字段；保存后回到来源列表并高亮。
  - 时间与数值：UTC 存储、本地时区显示；数值按精度四舍五入；统一日期格式。
  - 安全：敏感字段脱敏；危险操作二次确认；操作写入审计。
  - 性能：大表虚拟滚动、接口分页与延迟加载；数据轮询采用指数退避与失焦暂停。

## 12. 部署方案与选型

### 方案 A：边缘/无服务器（推荐入门）

- 选型确认（本项目采用）
  - 运行平台：Cloudflare Workers（HTTP API）+ Pages Functions（可选）
  - 调度：Workers Cron Triggers（分钟粒度）、可按需引入 Durable Objects/Queues
  - 状态与配置：D1（规则/日志关系数据）、KV（最新价与去重键）、Queues（异步投递）
  - 前端：静态站点（Pages）+ 后台使用同域 API
  - 注意：所有配额与限制以官方平台页面为准（/workers/platform/limits）

- 架构拓扑（方案 A 实施）
  - HTTP Worker：对外提供 REST API（规则/标的/Webhook/日志）
  - Scheduled Worker：按计划采集行情（轮询源）并写入 Price Bus（KV/D1）
  - 规则评估：在采集后立即执行（同触发器进程内），产生 Alert 并写入队列
  - 投递 Worker：消费队列，调用飞书/企微/钉钉 Webhook，记录 Delivery 日志
  - 可观测：Workers Analytics/Logs + 指标聚合（简版：D1 表 + 仪表盘页面）

- 绑定与配置（wrangler.jsonc 示例要点）
  - d1_databases：主库（goldwatch_db）
  - kv_namespaces：latest_quotes（最新价）、dedupe_keys（幂等窗口）
  - queues.producers/consumers：alerts_queue（投递任务）
  - vars：配置常量（如默认冷却时间）；secrets：第三方密钥（通过 wrangler secret）
  - 修改 bindings 后运行 wrangler types 以更新 TS 类型

- 采集策略（适配边缘限制）
  - Cron 最小粒度为分钟级，适合低频/分钟内更新的数据源；
  - 若需更低延迟：
    - 可使用“外部推送→HTTP Worker”模式（第三方在价格变动时回调）；
    - 或将“高频流”下沉至其他服务，边缘只做入站合流与规则评估；
  - 最新价进入 KV；关键 Tick 同步到 D1 以便审计与回放。

- 可靠性与限额对策
  - CPU 时间/内存限制：拆分为短任务（采集→评估→入队），投递异步化；
  - 请求并发与速率：对外 Webhook 投递加速率限制与指数退避；
  - 失败重试：队列消费者维护最大重试与死信策略；
  - 平台错误对照：参考官方错误文档（observability/errors）做分级处理。

- 部署流程（建议）
  - 开发：npx wrangler dev（本地模拟）；
  - 环境：staging/prod 使用不同 D1/KV/Queue 绑定；
  - 发布：npx wrangler deploy；
  - 监控：wrangler tail 查看实时日志；定期巡检投递成功率。

### 方案 B：Node 服务 + 队列

- Web/API：Node + NestJS/Express。
- 任务队列：BullMQ/Redis Streams；数据库：PostgreSQL。
- 适合更高吞吐与自定义网络连接（长 WS）。

### 方案 C：混合

- 将采集/规则/投递各自微服务化，按需扩容；公共数据库+指标平台。

选择建议：

- 日行情/中低频：A 足够；
- 高频/毫秒级延迟：B 或 C，更灵活的 WS 与内存状态。

## 13. 安全与合规

- Webhook URL/Secret 加密存储，不在日志中输出明文；仅在发送时解密至内存。
- 设置最小权限 RBAC；操作审计日志（谁在何时修改了规则/密钥）。
- 出站请求限制与 allowlist；防止 SSRF。
- 请求签名与验签（对外开放 API 时）。

## 14. 性能与可靠性

- 目标：秒级触达；从 Tick 到投递 < 1s（取决于数据源与平台限流）。
- 限流：对外投递按渠道与域名限速，失败退避。
- 缓存：最新价存内存+KV，减少 DB 压力。
- 灰度：规则变更热更新，先对单标的生效，逐步全量。
- 回放：支持离线 Tick 回放验证规则。

## 15. 可观测性

- 指标：采集 TPS、处理延迟、触发数、投递成功率、各渠道耗时、错误分布。
- 日志：结构化日志（TraceId/AlertId），错误堆栈聚合。
- 告警：系统异常（连续失败、延迟高于阈值）上报至维护群。

## 16. 测试与验收

- 单元测试：规则判定、去抖动、签名与模板。

## 18. 规则启停（Enable/Disable）

- 状态含义
  - active=true：规则参与评估与触发；
  - active=false：规则被跳过，不再触发新告警；历史状态保留；
  - 可选：停用时是否清理 state（cooldown、inWindow、refPrice）由参数控制。

- 引擎行为
  - 评估入口先判断 active；为 false 直接返回；
  - 停用→启用时：可选择“保留状态”或“复位状态”，避免启用瞬间误触发。

- API（新增）
  - POST /api/rules/:id/enable
    - body：{ resetState?: boolean }（默认 false）
    - 行为：将 active 置 true；若 resetState=true 则清理 rule_states 对应字段
  - POST /api/rules/:id/disable
    - body：{ clearCooldown?: boolean }（默认 true）
    - 行为：将 active 置 false；可选清理冷却窗口，保留最近值与参考价用于审计
  - POST /api/rules/batch-toggle
    - body：{ ids: string[], active: boolean, resetState?: boolean }
    - 行为：批量启停，适合交易时段或维护窗口操作

- 存储变更
  - rules.active：已有字段直接生效；
  - rule_states：新增字段可选 reset 标记（如 resetAt、resetBy）。

- 管理控制台（UI）
  - 在规则列表与详情页提供“启用/停用”切换；
  - 停用时弹出二次确认，可选是否清理状态/冷却；
  - 支持批量选择后统一启停；
  - 操作记录写入审计日志（操作人、时间、策略）。

- 使用场景
  - 行情极端波动期间临时停用部分规则；
  - 交易时段切换时按计划批量启用/停用；
  - 调整参数前先停用，验证后再启用，确保无误触发。

## 19. 用户登录认证（简化方案：环境变量 Basic Auth）

- 目标与范围
  - 本项目作为内部自用系统，不引入用户数据库与注册流程；
  - 部署时通过环境变量指定单一管理员用户名与密码；
  - 管理控制台（/admin）与受保护 API（/api/**，除 /api/public/**）均需认证。

- 环境变量约定（以 Cloudflare Workers 为例）
  - ADMIN_USER：管理员用户名（通过 wrangler secret 管理）
  - ADMIN_PASS：管理员密码（通过 wrangler secret 管理）
  - 设置示例：
    - wrangler secret put ADMIN_USER
    - wrangler secret put ADMIN_PASS
  - 注意：不要在代码仓库或日志中以明文形式出现用户名/密码。

- 认证方式：HTTP Basic Auth（最简）
  - 请求需携带头：Authorization: Basic <base64(user:pass)>
  - 未携带或验证失败时返回：
    - 401 Unauthorized
    - 响应头：WWW-Authenticate: Basic realm="GoldWatch"
  - 比较要求：
    - 使用常数时间比较（constant-time compare）避免时序侧信道；
    - 仅接受 ASCII 可见字符；异常输入视为失败。
  - 无状态特性：
    - 不依赖服务端会话；适合边缘函数与多实例；
    - 浏览器访问 /admin 将弹出原生认证对话框（或通过预先输入 URL+凭据）。

- 可选增强（保留为开关）
  - 会话 Cookie：认证通过后签发短期 HMAC Cookie（如 goldwatch_sid，15 分钟），减少浏览器重复弹窗；
  - IP 白名单：在私网或固定出口时增加后端 allowlist；
  - 速率限制：对失败的 Basic 尝试做 IP 粒度限速（KV 计数器 + 退避）。

- 路由与中间件策略
  - 受保护资源：
    - GET/POST/PATCH/DELETE /api/**（除 /api/public/**）
    - GET /admin/\*\*（管理控制台静态与数据接口）
  - 放行资源：
    - /api/public/\*\*（若将来提供无需认证的公开只读接口）
    - 静态首页或产品说明页（可选）
  - 在 Worker 入口添加认证中间件，对受保护路径进行 Basic 校验。

- API 行为规范（受保护接口）
  - 未认证或认证失败：返回 401 + WWW-Authenticate；
  - 不返回具体是哪项凭证错误；不回显输入；
  - 日志仅记录失败计数与来源（脱敏），不记录 Authorization 内容。

- 集成与部署（方案 A 环境）
  - 绑定 secrets 后，npx wrangler deploy 部署；
  - 若存在多个 Worker（API/投递/调度），仅对对外 HTTP 暴露的 API Worker 启用认证；
  - Pages 前端管理台可通过同域 Worker 路由（/admin/\*\*）受保护访问。

- 使用示例（测试）
  - 访问 API：
    - curl -u "$ADMIN_USER:$ADMIN_PASS" https://your-domain/api/rules
  - 访问控制台：
    - 浏览器打开 https://your-domain/admin，输入部署时配置的用户名与密码。
